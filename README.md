# МЕТ — Информационная система прослеживаемости и управления несоответствиями

MES + QMS система для машиностроительного предприятия (контрактная механообработка).
Отслеживает жизненный цикл деталей от договора до отгрузки: электронные МСК,
учёт операций на планшетах в цеху, регистрация и согласование актов несоответствия,
печать этикеток через BarTender, импорт данных из Excel.

Полное описание проекта — в [`Docs/01_PROJECT_CONTEXT.md`](Docs/01_PROJECT_CONTEXT.md).

## Статус

**Итоговая реализация. Этапы 1–3 завершены (23.10.2026).**

**Этап 3 — API производственного потока (29 тестов):**
- справочники (чтение) + заказчики (добавление технологом);
- МСК: создание с конструктором маршрута (исполнитель и наладка — из
  справочника типовых операций), списки с фильтрами, карточка, правка
  (срок/флаги — всегда; реквизиты — только черновик; количество не меняется),
  запуск в производство (технолог), нумерация «NN/YY» автоматически;
- «Мои работы» (GET /work/queue): операции с доступным остатком по
  роли+профессии, мастер видит весь цех; частично сданная партия сразу
  видна следующему исполнителю;
- закрытие операции (POST /work/operations/{id}/submit): годные (мгновенная
  передача дальше), несоответствия (изъятие), наладка (первая деталь
  годна/забракована — партия уменьшается); лимиты «не больше остатка»;
- лист предъявления: история предъявлений операции с №№ деталей и станком;
  контролёр ОТК пишет замечания;
- кооперация (участок 5555): отправка (день, количество), приёмка (годные
  сразу идут дальше, брак, галочка «есть документы»), сводка по партии;
  внешние операции не попадают в очереди исполнителей;
- отгрузка: список готовых (после финального контроля) с остатком «сколько
  отгрузить», отметка (роль ОТК/директор или персональное право «shipping»),
  лимит по годным, история; статус «Отгружена» — когда отгружены все годные.

**Этап 1 — база данных:** модели всех сущностей + миграция Alembic (20 таблиц):
справочники (заказчики с маскировочными номерами, участки 0100–5555, группы
оборудования, 49 станков предприятия, типовые операции с исполнителем и
наладкой, материалы, типы дефектов, причины НП), пользователи с ролями/
профессиями и гибкими правами, МСК (флаги ВП/ГПХ/давальческий, категория А/Б,
срок, остаток к отгрузке), операции маршрута, лист предъявления, кооперация,
карты НП, отгрузки, аудит. Нумерация «порядковый в году/YY». БД: разработка —
SQLite, production — PostgreSQL (миграции общие).

**Этап 2 — аутентификация и права:** JWT-вход (`POST /api/v1/auth/login`),
профиль (`GET /auth/me`), смена пароля; управление пользователями (админ):
список/создание/правка/отключение, сброс пароля, **персональные права по
аккаунтам** (известное право — «shipping», отметка отгрузки); зависимости
`require_roles` / `require_permission` для всех будущих эндпоинтов; вход и
ключевые действия пишутся в журнал аудита. Пароли PBKDF2, токен 8 часов,
секрет — `SECRET_KEY` в .env. 25 тестов зелёные; smoke-проверено на dev-БД
(admin/admin — сменить после первого входа).

Демо-итерации 1–4 (фронтенд на мок-данных, витрина /showcase) сохранены до
подключения реального API (этап 5).

История демо-итераций:

Итерация 3 (завершена): **сквозная логика производственного потока**
(демо-стор в памяти страницы):

```
Создание МСК (технолог, конструктор маршрута)
  → Запуск в производство (технолог; партия встаёт на первую операцию)
  → «Мои работы»: единая очередь для всех исполнителей
      (операторы по профессии: станочник/слесарь/заготовщик; контролёры ОТК;
       мастер видит весь цех). Наладка первой детали — отдельный шаг.
  → Сдача операции (годные N / брак M): годные автоматически передаются
      на следующую операцию; брак — карта НП (изолятор)
  → … до конца маршрута …
  → Отгрузка (ОТК/директор): отметка количества и даты → «Отгружена»
```

Решения по потоку: запуск — технолог; передача между операциями — автоматическая
после сдачи; частичная сдача разрешена; исполнители — роль «Оператор» с профессией
в профиле, контрольные операции — роль ОТК; отгрузка — начальник ОТК / директор
по качеству (гибкая настройка доступов по аккаунтам — в бэклоге).

Итерация 4 (доработки потока): закрытие операции — один диалог с выбором
«Годные / Несоответствия»; мгновенная попозиционная передача (частично сданная
партия сразу видна на следующей операции); прогресс партий — квадратиками
(подсказка показывает «Вып: N из M шт.»); исполнитель и обязательность наладки —
свойства типовой операции из справочника (конструктор МСК их не запрашивает);
наладка первой детали всегда с предъявлением ОТК, забракованная первая деталь
уменьшает партию на 1; форма карты НП автоподставляет МСК, операцию и количество
при создании из работы.

На витрине (`/showcase`, группа «Очередь работ») — три варианта представления
очереди: карточки (реализовано в /app/workshop), компактный список, канбан-поток.

Итерация 2 — выбранные интерфейсы (карты НП по форме 32-26, дашборд, МСК и т.д.).
Backend — каркас с health-эндпоинтом и настройкой под PostgreSQL.

## Запуск (разработка)

### Backend

```bash
cd backend
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -r requirements.txt -r requirements-dev.txt
copy .env.example .env        # при необходимости поправить DATABASE_URL
pytest                        # тесты
uvicorn app.main:app --reload # http://localhost:8000, docs: /docs
```

### Frontend

```bash
cd frontend
npm install
npm run dev                   # http://localhost:5173 → витрина вариантов
npm run build                 # production-сборка (tsc + vite)
```

- `/showcase` — витрина вариантов интерфейса (главная страница итерации);
  для каждой страницы системы — варианты A/B/C, переключение в верхней полосе.
- `/app` — скелет рабочего приложения: демо-вход (любой логин/пароль +
  выбор роли), ролевой доступ к разделам имитируется.
  Реальная аутентификация — в следующих итерациях.
